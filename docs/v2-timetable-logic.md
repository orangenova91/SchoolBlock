# 시간표 생성 로직 v2

v2는 기존 생성 로직(v1)을 그대로 둔 채, 같은 입력 단계(1~7단계)를 쓰면서
마지막 "시간표 생성" 단계만 개선한 비교 검토용 로직이다. v1과 v2는 시간표마다
선택되며(`terms.logicVersion`), 최종 검토 후 하나만 남길 예정이다.

- v1 엔진(`lib/timetable.ts`)은 수정하지 않았다.
- 공용 파일의 변경은 모두 `logicVersion === "v2"`일 때만 동작이 달라진다.
- SET 블록 위치는 v2에서도 고정이다. SET 이동은 전체 단계를 조정하는 v3에서 다룬다.

---

## 1. 사용 방법

1. 목록 화면 "시작하기"의 **새 시간표 작성(v2)** 로 만든다. 목록과 단계 화면에 `v2` 표시가 붙는다.
2. 1~7단계(학반·요일 → 교과 → 교사 → SET → 선 수업 → 배정 불가 → 추가 조건)는 v1과 같다.
3. 시간표 생성 단계에 들어오면 화면이 먼저 열리고, 이어서 **사전 검사**가 자동으로 진행된다.
4. 사전 검사를 통과하면 **시간표 배치**로 생성한다. 통과하지 못하면 배치 버튼이 막힌다.
5. 필요하면 **선호 조건 가중치(v2)** 를 바꾼 뒤 다시 배치한다.

v2에는 "동일 교과 우선 배치"·"점심시간 우선 배치" 버튼이 없다. 추가 조건에서 켠
기능은 시간표 배치 한 번 안에서 자동으로 반영된다.

---

## 2. 전체 흐름

```
[화면 진입]
  └ 화면 데이터 로딩 (사전 검사 없음, ~0.1초)
  └ 자동 사전 검사
       ├ 조건이 지난 검사와 같으면 → 저장된 결과 표시 (재판정 안 함)
       └ 다르면 → ① 빠른 검사(수 ms) → ② 정확 판정(최대 20초) → 결과 저장
[사전 검사 버튼]  항상 ①② 를 새로 실행하고 저장값 갱신
[시간표 배치]
  └ 사전 검사 (저장값과 조건이 같으면 재사용)
  └ 배치 불가로 증명되면 → 배치하지 않음 (409, 기존 결과 보존)
  └ 배치 가능하면 → 정확 판정이 찾은 미배치 0 배치안을 초기 배치로
                  → 교환 개선(담금질)으로 선호 점수를 낮춤 (최대 30초)
                  → 저장
```

## 3. 사전 검사

### 3.1 빠른 검사 – 최소 미배치 하한 (`lib/timetable-feasibility.ts`)

공통 수업(1시간 단위)과 칸(요일·교시)을 이분 그래프로 보고, 조건 하나를 뺀
완화 문제 두 개를 최대 매칭으로 정확히 푼다.

- **반 기준**: 반마다 "남은 수업 ↔ 그 반의 빈칸 중 담당 교사도 비어 있는 칸"
- **교사 기준**: 교사마다 "남은 수업 ↔ 그 교사의 빈 시간 중 해당 반도 비어 있는 시간"

짝짓지 못한 수 = 수업 수 − 최대 매칭 (Hall/König 정리: max(|S| − |N(S)|)).
완화 문제에서도 들어갈 자리가 없는 수업은 실제로도 반드시 미배치이므로
`max(반 기준 부족 합, 교사 기준 부족 합)`이 최소 미배치의 **하한**이다.
반·교사를 따로 보기 때문에 둘이 동시에 걸리는 경합은 못 잡는다(필요조건).

고정 칸은 생성기와 같은 `buildSeedTimetableCells`(SET·SET과 겹치지 않는 선 수업)에
순환 SET 교사(`teachersBusyForGradeSetAtSlot`)와 배정 불가를 더해 계산한다.

### 3.2 정확 판정 – 정수계획법 (`lib/timetable-exact-check.ts`)

[HiGHS](https://highs.dev/) 풀이기의 WebAssembly 빌드(`highs` 패키지)로 푼다.

- 변수: `x[g,s] ∈ {0,1}` 수업 묶음 g(교사·반·교과)의 1시간을 칸 s에 넣음
  (반이 비고 교사가 SET·선 수업·배정 불가로 막히지 않은 칸만),
  `u[g] ≥ 0` 정수 g의 미배치 시간
- 제약: `Σ_s x[g,s] + u[g] = 시수[g]`, 반 한 칸에 1개 이하, 교사 한 시간에 1개 이하
- 목표: `Σ u[g]` 최소화

풀이기가 "Optimal"로 끝나면 목표값이 **정확한 최소 미배치 수**다.

| 결과 | 의미 | 처리 |
|---|---|---|
| `feasible` | 미배치 0 배치가 존재함(증명) | 배치 진행. 찾은 배치안을 v2 초기 배치로 사용 |
| `infeasible` | 최소 미배치 ≥ 1 (증명) | 배치 차단. 남는 수업 예시를 표시 |
| `unknown` | 20초 안에 증명 못 함(`timeout`) 또는 풀이기 오류(`error`) | 빠른 검사로 판단. 하한이 0이면 기존 생성기로 초기 배치 |

빠른 검사가 놓치는 경우의 예(단위 테스트에 포함): 반 2개가 월·화 2교시씩 꽉 찼고,
월 2교시에 두 교사가 배정 불가라 그 칸에는 두 반 모두 같은 한 교사만 올 수 있다.
반 기준·교사 기준으로는 각각 자리가 있지만 실제로는 1시간이 반드시 남는다.

### 3.3 배치 자유도 (경우의 수 추정)

정확한 개수 세기는 #P-완전(행렬 퍼머넌트)이라 근사한다. 표시용 참고 지표이며,
배치 가능 여부는 정확 판정이 결정한다.

- 반 하나: 수업×칸 0/1 행렬 A의 퍼머넌트 ÷ (같은 교과 시수의 순서 m!).
  상한은 Bregman–Minc `perm(A) ≤ Π(rᵢ!)^(1/rᵢ)`,
  하한은 Sinkhorn 정규화 `A = D₁SD₂` 후 Gurvits `perm(S) ≥ Π(1−Sᵢⱼ)^(1−Sᵢⱼ)`.
- 반 사이: 반별 곱은 교사 겹침까지 세므로 상한. 추정치는 S를 주변확률로 보고
  교사·시간마다 `P(최대 1개 반)`을 독립 근사로 곱한다.
- 소규모 검증(전수 탐색 121건): 추정치는 실제보다 평균 1자리(약 10배) 작음.
  실제 규모에서는 10^170~10^300 수준으로 나온다.

### 3.4 결과 재사용 (`lib/timetable-check-cache.ts`)

검사 입력(교사·교과·학반·요일·SET·순환 배정·선 수업·배정 불가)을 고정된 순서로
직렬화한 SHA-256을 키로 `v2PlacementChecks` 컬렉션에 학기당 1건 저장한다.

- 자동 검사·생성 직전 검사: 키가 같으면 저장값을 쓴다(조건이 그대로면 판정 1회).
- 수동 검사: 항상 새로 판정해 저장값을 갱신한다.
- `unknown` 결과는 저장하지 않는다(다음에 다시 시도).
- 검사 로직을 바꾸면 `CHECK_CACHE_VERSION`을 올려 이전 저장값을 무효화한다.
- 학기 삭제·데모 계정 정리 시 `TERM_CHILD_COLLECTIONS`로 함께 삭제된다.

## 4. 생성 – 교환 개선 (`lib/timetable-improved.ts`)

### 4.1 초기 배치

- 정확 판정이 `feasible`이면 그 배치안(미배치 0)을 쓴다.
- 아니면(판정 `unknown`) 기존 `generateTimetable`로 2.5초 동안 만든다.

### 4.2 점수

| 항목 | 1건당 점수 |
|---|---|
| 교사 중복, 배정 불가 위반 (필수) | 1000 |
| 점심시간 연강 | 가중치 (기본 3) |
| 3연강 | 가중치 (기본 2) |
| 동일 교과 같은 날 중복 | 가중치 (기본 3) |

추가 조건에서 꺼진 항목은 점수에 넣지 않는다. 선호 가중치 최대 10이라
필수 조건은 항상 먼저 지켜진다.

### 4.3 탐색

- 같은 반 안에서 두 칸(공통 수업 또는 빈칸)을 맞바꾼다. 반마다 여유 칸이 0인
  시간표에서도 움직일 수 있다. SET·선 수업 칸은 움직이지 않는다.
- 교환마다 바뀐 교사 2명의 해당 요일과 그 반의 해당 요일만 다시 계산한다
  (초당 수십만 회 평가).
- 담금질: 점수가 나빠지는 교환도 온도에 따라 일정 확률로 받아들여 국소 최적을 벗어난다.
- 종료 규칙:
  - 한 바퀴 8초 동안 온도 4 → 0.05로 식힌다.
  - 바퀴가 끝나면 최저 상태로 돌아가 온도 0.8로 다시 데워 한 바퀴 더 돈다.
  - **다시 데운 바퀴가 최저 점수를 한 번도 낮추지 못하면** 종료한다
    (첫 바퀴는 종료 판단에서 제외).
  - 점수 0(선호 조건 위반 없음)이면 즉시 종료한다.
  - 전체 상한 30초.
- 끝까지 남은 교사 중복이 있으면 해당 공통 수업을 빼서 미배치로 돌려준다
  (정확 판정 `feasible`에서 출발하면 생기지 않는다).

### 4.4 선호 조건 가중치 (`lib/v2-weights.ts`)

- 생성 단계 화면의 "선호 조건 가중치 (v2)"에서 항목별로 1·2·3·5·10 중 선택.
- `generationPreferences.v2Weights`에 저장(v1은 이 필드를 읽지 않고, v1 저장 시에도 유지됨).
- 복제·내보내기·가져오기 시 함께 복사된다.

MongoDB 스키마 마이그레이션은 필요 없다. 필드가 없으면 v1/기본값으로 동작한다.

|---|---|---|
| `terms` | `logicVersion?: "v2"` | v2 시간표 표시 |
| `generationPreferences` | `v2Weights?: { lunch, triple, sameDay }` | v2 선호 가중치 |
| `v2PlacementChecks` (새 컬렉션) | `termId, inputKey, report, solutionCells, checkedAt` | 사전 검사 결과 |

## 6. API

| 메서드 · 경로 | 설명 |
|---|---|
| `POST /api/terms` | `logicVersion: "v2"`를 받으면 v2 시간표로 생성 |
| `GET /api/terms/[id]/timetable` | v2면 `term.logicVersion`, `v2Weights` 포함 (사전 검사는 하지 않음) |
| `POST /api/terms/[id]/timetable` | v2: 사전 검사(재사용) → 불가면 409 → 가능하면 v2 생성. `maxDuration = 60` |
| `POST /api/terms/[id]/timetable/feasibility?mode=cached` | 조건이 같을 때의 저장된 결과 (없으면 `null`) |
| `POST /api/terms/[id]/timetable/feasibility?mode=quick` | 빠른 검사만 |
| `POST /api/terms/[id]/timetable/feasibility` | 빠른 검사 + 정확 판정을 새로 하고 저장. `maxDuration = 40` |
| `PUT /api/terms/[id]/timetable/weights` | v2 가중치 저장 |
| `POST .../timetable/lunch-priority`, `.../same-day-subject-priority` | v2 시간표면 400 |

## 7. 측정 결과 요약

학교 조건 36가지에 대한 성능 측정은 [v2-performance.md](v2-performance.md) 참고
(배치 가능 31개 시나리오에서 생성 93회 모두 미배치 0, 배치 불가 5개 모두 차단).

측정 데이터: A(테스트 시간표, SET 있음, 20개 반), B(데모 SET+선 수업), C(데모 SET 없음, 12개 반)와
이를 변형한 조건(동일 교과 확대, 선 수업 +20%, 배정 불가 15~25%, 교사 통합, 복합).

- **미배치**: v1(우선 배치 사용)은 대부분 2~10교시 미배치. v2는 배치 가능한 모든 조건에서 0.
- **배치 불가 조건**: 정확 판정 최솟값과 v2 결과가 일치(A 복합 5, B 복합 3, C 복합 1).
  v1의 빠른 하한(3, 2, 0)보다 정확.
- **품질**: A 데이터 기준 3연강 47 → 7(−85%). 점심 연강은 25 근처가 하한(SET 고정이 원인).
- **우선 배치 단계**: v2에서는 결과에 기여하지 않음(유지율이 우연 수준, 품질 동일) → 제거.
- **종료 규칙**: 30초 단일 냉각과 같은 품질을 평균 21~25초에 달성.
- **규모**(C를 1~4배): 반 48개·1680시수에서 빠른 검사 33ms, 정확 판정 5.3~5.8초, 생성 4.2초.
- **가중치**: 테스트 데이터는 각 조건이 하한 근처라 차이가 작음. 맞교환 방향은 확인됨
  (3연강 가중치↑ → 3연강↓, 동일 교과↑).

## 8. 한계와 남은 과제

- SET 위치 고정이 점심 연강·3연강의 하한을 결정한다 → v3에서 SET 이동 검토.
- 생성(최대 30초)과 정확 판정(최대 20초) 동안 Node 서버가 묶인다 → 배포 방식 확정 시 검토.
- 정확 판정은 큰 학교·빡빡한 조건에서 20초를 넘길 수 있다(그때는 빠른 검사로 판단).
- 실제 학교 데이터로의 검증, 특히 조건끼리 부딪히는 경우의 가중치 효과 확인이 필요하다.
- 배치 자유도는 큰 규모에서 배치 가능 여부를 보장하지 않는 참고 지표다.
