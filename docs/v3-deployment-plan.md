# v3 배포 방안 (2026-10-17 검토)

[배포 검토](v3-deployment-review.md)의 후속이다. 사용자 조건과 버셀 최신 문서(2026-10 확인)를 기준으로, 시간표 계산을 어디서 어떻게 돌릴지 정리한다.

## 확정 사항 (2026-10-17 사용자 결정)

| 항목 | 결정 |
|---|---|
| 언어 | **바꾸지 않는다** (Next.js·Node.js 그대로) |
| 지금 | 로컬 개발 서버(서버 안 계산 스레드)로 테스트를 계속한다 |
| 서비스 | **버셀 Pro**를 우선 검토한다 (함수 구간 실행, 3절) |
| 버셀 Pro가 어려우면 | 필요한 사양에 맞는 서버 호스팅(4.3절) — 웹은 버셀에 두고 계산 서버만 따로 두는 구성부터 검토 |
| 동시 계산 기본값 (버셀 Pro 기준) | **10개** (아래) |

### 동시 계산 기본값: 10개 (`V3_MAX_RUNNING=10`, 배포할 때 넣을 설정)

| 근거 | 내용 |
|---|---|
| 기다림 | 30명이 한꺼번에 요청해도 마지막 사람이 약 40분 안에 결과를 받음 (2.1절). 5개면 약 1시간 10분, 20개면 약 20분 |
| 버셀 한도 | 함수는 최대 30,000개까지 자동으로 늘어나므로 10개는 여유가 큼. 함수 1개 = 1 vCPU·2 GB |
| 비용 | 계산이 돌 때만 냄. 10개가 5분 돌면 약 $0.17. 몰리는 달 예상 약 $15 (Pro 월 크레딧 $20 안) |
| 데이터베이스 | 함수마다 연결이 몇 개씩 생김. 10개면 수십 개 수준이라 MongoDB Atlas 무료 등급 한도(500)보다 훨씬 적음. 계산 함수의 연결 수 상한은 작게 둔다 (`maxPoolSize` 5 안팎) |
| 학기당 | 한 학기(시간표)는 한 번에 1개만 실행, 대기 3개 (이미 구현). 그래서 10개는 서로 다른 10개 학교·시간표 |

조정 기준
- 대기가 길다는 의견이 많으면 20까지 올린다 (비용은 쓴 만큼만 늘고, 계산 1개의 속도는 같음)
- 버셀이 계산을 한 CPU에 몰아 넣는 것이 PoC에서 확인되면, 막는 장치를 넣기 전까지 낮춘다
- 서버 호스팅으로 가면 상한은 **코어 수 − 1** (12 vCPU면 10~11)

### 로컬 테스트 설정

- 개발 서버(`npm run dev`)는 계산 작업자를 자동으로 켠다. 동시 계산은 `V3_WORKER_CONCURRENCY`(기본 1)
- 여러 학교를 동시에 시험하려면 `.env.local`에 `V3_WORKER_CONCURRENCY=4` 처럼 넣고 개발 서버를 다시 시작한다 (이 PC는 논리 코어 32개)

## 0. 조건 (사용자)

- 가장 원하는 것: **지금처럼 버셀**을 쓰면서, 계산 중에도 서버가 멈추지 않는 안정적인 구조
- 사용 패턴: 평소에는 거의 없음. 학기 시작 전 특정 기간에 **수 명~수십 명이 동시에** 생성을 요청
- 목표: 최소 수 개, 가능하면 **10개 동시 계산**. 넘치면 대기열에 쌓아 순서대로 처리
- 페이지를 떠났다 돌아와도 진행 상황과 결과를 볼 수 있어야 함 (→ 이미 구현: 작업·결과가 DB에 있음)

## 1. 결론

| 질문 | 답 |
|---|---|
| 버셀로 가능한가 | **Pro 요금제면 가능하다** (함수 한 번에 5분 구간 하나). Hobby는 불가 (상업적 사용 금지, 월 CPU 4시간, 예약 실행 하루 1번) |
| 동시 계산 몇 개 | 버셀 함수는 요청마다 따로 늘어나므로 **10개 이상도 가능**. 실제 상한은 우리가 정함(기본 10). 넘치면 대기열 |
| 남은 위험 | 버셀이 계산 두 개를 같은 인스턴스(CPU 1개)에 몰아 넣을 수 있는지 등 3가지 → **1~2일 시험(PoC)으로 확인** |
| 시험이 실패하면 | 웹은 버셀 그대로, **계산만 별도 서버**(VPS 또는 버셀 Daemons)로. 코드는 이미 준비됨 |
| 노드로 안정 운영 가능한가 | **가능하다.** 자바로 바꿀 필요 없음 (4절) |
| 가장 큰 제약 | **CPU 코어 수.** 계산 1개가 코어 1개를 100% 씀. 메모리는 계산 1개에 0.3~1 GB |

## 2. 계산은 왜 무겁고, 무엇이 제약인가

비유: 계산 하나는 **요리사 한 명이 한 요리를 5분간 쉬지 않고 만드는 것**이다. 요리사(CPU 코어) 한 명은 한 번에 요리 하나만 할 수 있다. 조리대(메모리)는 요리 하나에 일정한 넓이가 필요하다.

| 자원 | 계산 1개당 | 10개 동시 | 근거 |
|---|---|---|---|
| CPU | 코어 1개 100% (5분 내내) | 코어 10개 | HiGHS(WebAssembly)·탐색 모두 단일 스레드 |
| 메모리 | 평균 0.3~0.6 GB, 최대 약 1 GB | 10~12 GB (+웹·운영체제 여유) | 계산기 메모리 1 GB를 넘으면 구간을 끝냄 |

→ **CPU가 먼저 바닥난다.** 코어보다 많은 계산을 동시에 돌리면 모두가 느려진다(요리사 한 명이 두 요리를 번갈아 하면 둘 다 늦어짐). 그래서 동시 계산 수를 코어 수에 맞춰 묶고, 나머지는 대기열에 둔다.

### 2.1 몰리는 기간의 대기 시간 (추정)

학교 하나의 평균 계산 시간을 12분으로 잡는다 (혼합 5분 구간 2번 + 하한 2분. 쉬운 학교는 5분 안에 끝나고, 어려운 학교는 30분까지). 30명이 한꺼번에 요청하면 총 계산량은 360분이다.

| 동시 계산 | 마지막 사람이 결과를 받기까지 |
|---|---|
| 1개 | 약 6시간 |
| 3개 | 약 2시간 |
| **10개** | **약 40분** |
| 30개 | 약 12분 (본인 계산 시간만) |

대기열은 5분 구간 단위로 돌아가며 처리하므로(이미 구현) 한 학교가 30분을 독차지하지 않는다. 모든 사람이 첫 결과를 먼저 받는다.

## 3. 버셀 안에서 하는 방법 (1순위)

### 3.1 버셀 제한 (2026-10 문서)

| 항목 | Hobby (무료) | Pro ($20/월, $20 사용 크레딧 포함) |
|---|---|---|
| 함수 한 번의 최대 실행 시간 | 300초 | 800초 (베타 1,800초) |
| 함수 메모리·CPU | 2 GB / 1 vCPU | 최대 4 GB / 2 vCPU |
| 동시 실행 | 자동 확장 (최대 30,000) | 같음 |
| 계산 요금 | 월 CPU 4시간·메모리 360 GB-시간 포함, 넘으면 다음 달까지 멈춤 | 사용한 만큼 (서울 icn1: CPU 시간당 $0.169, 메모리 GB-시간당 $0.014) |
| 예약 실행(cron) | 하루 1번 | 1분마다 |
| 사용 범위 | **개인·비상업 용도만** | 업무 용도 |

Hobby는 학교 대상 서비스에 맞지 않는다.
- 상업적 사용이 금지다.
- 한 달 CPU 4시간이면 학교 20곳 정도만 계산해도 다 쓴다.
- 함수 300초가 구간 5분과 겹쳐 여유가 없다.

### 3.2 구조: "함수 한 번 = 5분 구간 하나"

```
[사용자] 생성 버튼 ─▶ POST v3/jobs ─▶ MongoDB 대기열에 작업 저장 (이미 구현)
                              └─ 바로 "계산 함수"를 깨움 (응답은 즉시 돌려줌)
[계산 함수] /api/v3/worker/tick  (maxDuration 420초, 메모리 2 GB)
   ① 실행 중 작업 수 < 상한(기본 10)이면 대기 작업 하나를 가져감 (임대)
   ② 계산 스레드에서 5분 구간 실행, 2초마다 진행 저장 (이미 구현)
   ③ 결과 3개·중단점 저장 → 대기 작업이 남았으면 다음 계산 함수를 깨움
[예약 실행] 1분마다 tick 을 (빈자리 수만큼) 호출 → 빠진 것·끊긴 것을 다시 채움
[화면] 2.5초마다 상태 읽기 (이미 구현). 페이지를 닫아도 계산은 계속되고, 돌아오면 그대로 보임
```

비유: 식당 주문표(대기열)를 벽에 붙여 두고, 주문이 오면 **임시 요리사(함수)** 를 부른다. 요리사는 5분 동안 한 요리를 하고, 중간 상태를 기록해 두고 퇴근한다. 다음 5분은 새 요리사가 기록을 보고 이어 한다. 손님이 몰리면 요리사를 더 부르고(최대 10명), 손님이 없으면 아무도 부르지 않는다(**비용 0**).

이미 된 것
- 대기열·임대·중단점·공정 순번·진행 저장·결과 보관: 모두 MongoDB에 있음 (M4·M5)
- 작업자가 갑자기 끊겨도 임대가 끝나면 다른 함수가 중단점에서 이어 받음 (M4에서 확인)
- 페이지를 떠났다 돌아와도 진행·결과 확인 (M6)

해야 할 것 (코드)
1. `tick` 창구를 "구간 하나 실행 + 다음 함수 깨우기" 방식으로 다듬고, **전체 동시 상한**(`V3_MAX_RUNNING`, 기본 10)을 DB에서 지킨다
2. 작업을 만들 때 계산 함수를 바로 깨운다 (`after()`)
3. 계산 스레드 파일을 미리 빌드하고, 계산기(WASM) 파일을 함수 묶음에 포함 (`outputFileTracingIncludes`)
4. `vercel.json`: 1분마다 예약 실행, `tick` 함수의 maxDuration 420초
5. 한 인스턴스에서 계산이 둘 돌지 않게 막기 (3.4의 위험 ①)

### 3.3 비용 (서울 지역 기준 추정)

- 5분 구간 하나 (1 vCPU·2 GB): CPU 0.083시간 × $0.169 + 메모리 0.167 GB-시간 × $0.014 ≈ **$0.017 (약 25원)**
- 몰리는 달: 학교 100곳 × 작업 3번 × 구간 3개 = 900구간 ≈ **$15** → Pro의 월 $20 크레딧 안
- 평소: 계산이 없으면 0원
- 고정비: Pro 요금 **$20/월** (배포하는 사람 1명 기준)

### 3.4 시험(PoC)으로 확인할 위험 3가지

| 위험 | 내용 | 확인·대응 |
|---|---|---|
| ① 계산이 한 인스턴스에 몰림 | 버셀 Fluid compute는 한 인스턴스에서 여러 요청을 함께 처리할 수 있다. 원래는 데이터베이스를 기다리는 요청을 위한 기능이지만, CPU를 쓰는 계산 두 개가 같은 CPU에 들어오면 둘 다 느려진다. 문서에 CPU 기준으로 나누는지는 나와 있지 않다 | 계산 10개를 동시에 넣고 구간별 반복 횟수를 비교. 몰리면: 인스턴스마다 "계산 중" 표시를 두고 이미 계산 중이면 바로 돌려보냄(작업은 대기열에 남음) |
| ② 계산 스레드·WASM이 함수에서 도는가 | 개발에서는 TypeScript 원본을 `tsx`로 실행한다. 배포에서는 빌드한 JS와 WASM 파일이 함수 안에 있어야 한다 | 미리보기 배포에서 구간 하나 실행 |
| ③ 데이터베이스 연결 수 | 함수가 10개 뜨면 연결도 늘어난다 | MongoDB 요금제의 연결 한도 확인 (Atlas 무료 등급은 500개) |

PoC 기간: 1~2일. 이 셋이 통과하면 버셀 안에서 운영한다.

### 3.5 버셀 Daemons (참고, 공개 베타)

버셀에 상시 실행 작업자(Daemons)가 생겼다.
- 우리 코드의 "별도 작업자 프로세스"(`scripts/v3-worker.ts`)를 컨테이너로 그대로 돌릴 수 있다.
- Pro는 동시에 16 vCPU·32 GB까지 쓸 수 있다.

단점
- **자동으로 늘거나 줄지 않는다.** 켜 둔 대수만큼 계속 돌아서, 평소에도 비용이 든다.
  - 메모리 요금 기준 2 GB 인스턴스 1대 ≈ 월 $31. CPU 시간 요금은 따로다.
- 베타라 요금과 한도가 바뀔 수 있다.

쓰는 법: 몰리는 기간에만 대시보드에서 대수를 10으로 올리고, 끝나면 0으로 내린다. 함수 방식(3.2)이 PoC에서 막힐 때의 버셀 안 대안이다.

## 4. 서버 호스팅(VPS)으로 가면 (2순위)

### 4.1 노드로 안정 운영이 가능한가 → 가능

"계산이 서버를 멈춘다"는 문제의 원인은 언어가 아니라 **계산을 웹 요청과 같은 줄에서 돌린 것**이다. v3는 이미 계산을 별도 스레드·별도 프로세스로 분리했다. 측정 결과 계산 중에도 웹 응답 중앙값은 27 ms였다.

### 4.2 자바로 바꿔야 하는가 → 필요 없다

- 계산 시간의 대부분은 **HiGHS 계산기**(C++로 만든 것을 WebAssembly로 씀)와 알고리즘에서 나온다. 자바로 바꿔도 같은 계산기(또는 OR-Tools)를 불러 써야 해서, 얻는 것은 적고 다시 짜는 비용이 크다.
- 속도가 더 필요해지면 언어를 바꾸기보다 **HiGHS 원본(네이티브) 실행 파일을 쓰는 계산 전용 서비스**를 붙이는 것이 먼저다. WebAssembly보다 빠를 것으로 예상되지만, 배수는 측정이 필요하다.
- 스프링 부트 전환 비용(웹·API·인증 전체 재작성)에 비해 이득이 없다.

### 4.3 사양

| 목표 동시 계산 | vCPU | 메모리 | 비고 |
|---|---|---|---|
| 1 | 2 | 4 GB | 웹과 계산이 코어를 하나씩 |
| 3 | 4 | 8 GB | 이전 검토의 권장 |
| 6~7 | 8 | 16 GB | |
| **10** | **12** | **16~24 GB** | 목표 |

- MongoDB는 외부(지금처럼)로 둔다. 같은 서버에 두면 +2 GB, +1 vCPU.
- 문제: 1년 내내 12 vCPU를 빌려도 쓰는 기간은 몇 주다. 평소에는 비싼 서버가 놀고 있다.
- 구성: **웹은 버셀 그대로**, 계산 서버만 VPS에 두고 `scripts/v3-worker.ts`를 실행한다 (같은 `MONGODB_URI`, `V3_WORKER_CONCURRENCY` = 코어 수 − 1). 웹 이전이 필요 없다.
- 카페24 등 국내 VPS는 vCPU 수·요금·시간 단위 증설이 가능한지 확인해야 한다.

## 5. 추천과 진행 순서

1. **버셀 Pro + 함수 구간 실행 (1순위)**: 평소 0원, 몰리면 10개까지 자동으로 늘어남, 웹 구조 그대로
2. 서비스 전에 **PoC 1~2일**로 3.4의 위험 3가지 확인 (지금은 로컬 테스트를 계속)
3. PoC가 막히면: 웹은 버셀 그대로, 계산만 **버셀 Daemons**(몰리는 기간만 켬) 또는 **VPS 계산 서버**
4. 언어는 바꾸지 않는다 (확정)
