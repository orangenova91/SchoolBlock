# v3 배포 검토 (2026-10-17, 내용 검토만. 이전은 하지 않음)

현재 배포는 Vercel이다. 계산 작업(생성·진단)을 어디서 어떻게 돌릴지 검토한다.

## 1. "계산이 웹 서버를 멈춘다"는 문제

### 1.1 원리

- Node.js 프로세스 하나는 자바스크립트를 **한 줄(스레드 하나)로** 처리한다.
- 웹 요청은 대부분 "DB를 기다리는" 시간이라, 한 줄로도 많은 요청을 번갈아 처리할 수 있다.
- 시간표 계산은 기다림 없이 CPU를 계속 쓰는 일이다(탐색 반복, HiGHS 계산).
  - 계산하는 동안 그 줄은 다른 일을 하나도 못 한다.
- 비유하면 계산대 직원 한 명이 주문 사이사이 요리까지 하는 식당이다. 손님 한 명의 30분짜리 요리를 시작하면 그동안 다른 손님 주문도 받지 못한다.

### 1.2 지금 코드(v1·v2)

- 생성 API가 요청을 받은 그 자리에서 계산한다(최대 30초 + 판정 20초).
- 자체 서버 한 대라면, 그동안 그 서버의 모든 요청(다른 학교의 페이지 열기 포함)이 멈춘다.
- Vercel에서는 요청마다 실행 환경을 따로 띄워서 덜 드러난다. 다만 Fluid compute는 실행 환경 하나가 여러 요청을 함께 받을 수 있어, 같은 환경의 다른 요청이 느려질 수 있다.

### 1.3 해결 원칙

**계산을 웹 요청을 받는 줄에서 떼어 낸다.** 별도 작업 스레드·별도 프로세스·별도 함수 호출 중 하나로 옮기면 된다.

v3는 개발 단계부터 이 원칙을 따른다(작업 스레드). 이건 Node의 근본 한계가 아니라 **구조의 문제**다. CPU 계산을 별도 프로세스로 돌리는 것은 Node에서 흔하고 안정적인 방식이다.

## 2. 메모리 측정 (계산 프로세스 하나, 이 PC)

| 계산 | 학교 규모 | 60초 | 5분 |
|---|---|---|---|
| 탐색 | 21반 | 223 MB | — |
| 탐색 | 48반 | 293 MB | — |
| 탐색 | 60반 | 293 MB | — |
| 정수계획 단독 | 21반 | 236 MB | 358 MB |
| 정수계획 단독 | 48반 | 210 MB | — |
| 정수계획 단독 | 60반 | 513 MB | **878 MB** (계산기 내부 1.14 GB) |
| 혼합 | 48반 | 391 MB | 541 MB (계산기 내부 689 MB) |

- 탐색은 크기와 시간에 거의 상관없이 200~300 MB다.
- **정수계획 계산은 오래 돌수록 메모리가 늘어난다.**
  - 계산기(WebAssembly)는 한번 늘린 메모리를 줄이지 않고, 상한은 4 GB다.
  - 30분 단독 계산은 위험하다.
  - 대응: 5분 구간마다 계산기를 새로 만들어 메모리를 비운다. 중단점이 있어 이어 가는 데 손해가 없다(5단계 실험).
  - 대응: 정수계획 단독 작업의 메모리 상한을 정해 넘으면 그 구간을 끝낸다.
- 작업 하나의 예산은 **약 1 GB**로 잡는다 (60반 정수계획 5분 최악 기준).

## 3. 필요한 서버 사양

| 구성 요소 | 메모리 |
|---|---|
| 웹 서버(Next.js) | 0.3~0.5 GB (배포 빌드에서 다시 측정 필요) |
| 계산 작업 1개 | 평균 0.3~0.6 GB, 최악 약 1 GB |
| 운영체제·여유 | 0.5~1 GB |
| MongoDB를 같은 서버에 둘 경우 | +1~2 GB (외부 서비스(Atlas 등)면 0) |

계산은 작업 하나가 CPU 코어 하나를 다 쓴다(HiGHS JS는 단일 스레드).

| 등급 | 사양 | 동시 계산 | 비고 |
|---|---|---|---|
| 최소 | 2 vCPU · 4 GB | 1개 (나머지는 대기열) | DB는 외부. 웹과 계산이 코어를 하나씩 씀 |
| 권장 | 4 vCPU · 8 GB | 3개 | DB 외부 기준. DB를 같은 서버에 두면 8 GB에 동시 계산 2개 |
| 여유 | 8 vCPU · 16 GB | 6~7개 | 학교가 많아지면 |

## 4. Vercel에서 계산을 분리할 수 있는가

**가능은 하다. 다만 제약이 크다.**

| 항목 | Vercel 사실 (공식 문서) | v3에 주는 영향 |
|---|---|---|
| 한 번 실행 시간 | Hobby 최대 300초, Pro 최대 800초 (30분은 베타) | 5분 구간을 한 번 실행으로 처리 가능 (Hobby는 4분 30초 정도로 줄여야 안전) |
| 메모리·CPU | Hobby 2 GB · 1 vCPU 고정, Pro 2 GB 기본·최대 4 GB · 2 vCPU | 작업 하나(최대 약 1 GB)는 들어감 |
| 상시 작업자 | 없음 (요청이 끝나면 함수도 끝남) | 대기열을 돌리려면 "구간 끝 → 다음 구간 호출" 연쇄와, 끊긴 작업을 되살릴 정기 호출(cron)이 필요 |
| 실행 환경 공유 | Fluid compute: 한 실행 환경이 여러 요청을 함께 받을 수 있음 | 계산과 페이지 요청이 같은 환경에 섞이면 느려질 수 있음 → 계산용 경로를 따로 두는 설정 필요 |
| 요금 | Pro는 실제 CPU 사용 시간·메모리로 과금 | 학교가 많아지면 계산 시간만큼 비용 증가 |
| 사용 범위 | Hobby는 개인·비상업용 공정 사용 지침 적용 | 여러 학교가 쓰는 서비스면 Pro가 필요할 가능성 (확인 필요) |

정리:
- Vercel에서 v3를 돌리려면 "구간 호출" 방식(5단계 설계에 이미 포함)으로 계산을 쪼개야 한다.
- 대기열·재시도·정기 호출을 직접 꾸려야 한다.
- 계산량에 따라 비용이 늘어난다.
- 동작은 하지만, 운영 부담은 상시 서버보다 크다.
- Vercel의 작업 흐름(Workflow)·대기열 제품을 쓰면 이 부분을 덜 수 있는지는 별도로 확인해야 한다.

## 5. 서버 호스팅(VPS)으로 옮기면 해결되는가

**해결된다.** 상시 서버에서는 다음이 모두 자연스럽다.
- 웹 서버(Next.js)와 계산 작업자를 별도 프로세스로 띄운다 (PM2 같은 프로세스 관리자로 각각 관리).
- 작업자 수를 코어 수에 맞춘다 → 계산이 웹을 멈추지 않는다.
- 실행 시간 제한이 없다 → 5분 구간·30분 최대를 그대로 쓴다.
- 대기열은 MongoDB로 충분하다 (별도 서비스 불필요).

### Node.js로는 본질적 해결이 어려운가?

- **아니다.** 문제는 "웹 요청 처리와 같은 곳에서 계산한 것"이지 Node.js 자체가 아니다. 별도 프로세스로 떼면 안정적으로 돈다.
- 남는 한계는 **계산 한 건의 속도**다.
  - HiGHS JS는 작업 하나에 코어 하나만 쓴다.
  - 여러 코어를 한 작업에 쓰는 계산기(예: OR-Tools CP-SAT, 상용 계산기)는 Node에서 바로 쓰기 어렵다. 별도 프로그램 호출로는 가능하다.
- 이것은 "더 빨리, 더 좋은 해"의 문제이지 "안정적 운영"의 문제가 아니다.

## 6. 카페24 개발언어 VPS (Node.js) 검토

공식 FAQ 기준:

| 요금제 | 월 요금 (VAT 포함) | 메모리 | SSD | 트래픽 |
|---|---|---|---|---|
| DEV A | 33,000원 | 2 GB | 50 GB | 1.0 TB |
| DEV B | 66,000원 | 4 GB | 100 GB | 2.0 TB |
| DEV C | 132,000원 | 8 GB | 200 GB | 4.0 TB |
| DEV D | 220,000원 | 16 GB | 400 GB | 6.0 TB |

| 항목 | 내용 | v3 판단 |
|---|---|---|
| Node.js | Node.js 24, PM2로 프로세스 관리, Next.js 지원 | 이 프로젝트와 맞음 (package.json의 Node 24.x) |
| CPU(vCPU) 수 | **공개 자료에 없음** | 동시 계산 수를 좌우하므로 **반드시 문의** |
| DB | PostgreSQL·MariaDB 선택 | **MongoDB가 없음** → 외부 MongoDB(Atlas 등)를 쓰거나 직접 설치 |
| 백업 | 자동 백업 없음 | DB가 외부면 DB 쪽 백업 사용. 직접 설치하면 백업 구성 필요 |
| 요금제 변경 | 상위로만 가능 | 작게 시작해 키우기 좋음 |
| 메모리 재시작 예시 | FAQ 예시가 `max_memory_restart: '500M'` | 계산 작업자는 1 GB 이상으로 설정해야 계산 중 재시작되지 않음 |

판단:
- DB가 외부(Atlas)라면 **최소 DEV B(4 GB), 권장 DEV C(8 GB)**. 단 vCPU 수 확인이 먼저다(최소 2, 권장 4).
- MongoDB를 같은 서버에 설치하면 한 단계 위(DEV C 최소)가 필요하다.
- 운영 측면에서 Vercel보다 단순하다.
  - 상시 작업자, 시간 제한 없음, 고정 요금
- 대신 서버 관리(보안 업데이트, 장애 대응, 백업)를 직접 해야 한다.

## 7. 자바 스프링 부트로 바꾸는 안

| 관점 | 내용 |
|---|---|
| 얻는 것 | JVM의 진짜 다중 스레드, 성숙한 작업 실행 도구(스케줄러·배치), OR-Tools(CP-SAT) 같은 다중 코어 계산기를 직접 사용 → 계산 한 건이 더 빠르고 좋아질 가능성 |
| 드는 비용 | 서버 로직 전체 재작성: `lib` 약 13,600줄, API 라우트, 인증. 화면(Next.js)은 남기더라도 두 기술을 함께 운영해야 함. JVM 기본 메모리 0.5~1 GB 추가 |
| 위험 | 재작성 중 v1·v2 동작이 달라질 위험. 지금까지 실험한 계산(탐색·혼합)을 다시 이식·검증해야 함 |
| 판단 | **지금은 필요 없다.** 안정 운영은 Node + 별도 작업자로 해결된다. 나중에 "계산 품질·속도"가 부족하면, 전체 재작성 대신 **계산만 하는 별도 서비스**(자바 또는 다른 언어)를 붙이는 쪽이 비용이 훨씬 작다. 대기열·중단점·작업 상태 설계가 이미 그 형태라 계산 엔진만 바꿔 끼울 수 있다 |

## 8. 결론 (배포 단계에서 확정)

1. 계산은 어디서든 **웹 요청과 분리**한다 (v3 설계가 이미 그렇게 되어 있음).
2. 선택지는 두 가지다.
   - Vercel 유지: 구간 호출 + 정기 호출 + Pro 요금제 가능성
   - VPS 이전: 웹 + 작업자 프로세스, 사양은 최소 2 vCPU·4 GB, 권장 4 vCPU·8 GB
3. 카페24 DEV B/C가 후보다. **vCPU 수와 MongoDB 운영 방식(외부·직접 설치) 확인이 먼저**다.
4. 스프링 부트 전환은 지금은 하지 않는다. 계산 품질 한계가 확인되면 계산 전용 서비스를 붙이는 것을 우선 검토한다.

## 9. 구현 후 정리 (M7, 2026-10-17)

v3를 다 만든 뒤, 배포할 때 정해야 할 것을 실제 코드 기준으로 정리한다. 이전은 아직 하지 않는다.

### 9.1 실행 방식 3가지와 설정

| 방식 | 켜는 법 | 계산이 도는 곳 | 맞는 환경 |
|---|---|---|---|
| A. 서버 안 계산 스레드 | `V3_WORKER=thread` (개발 서버는 설정 없이 켜짐). 동시 계산 수 `V3_WORKER_CONCURRENCY` (기본 1) | 웹 서버 프로세스 안의 별도 스레드 | 늘 켜져 있는 Node 서버 1대 (VPS) |
| B. 별도 작업자 프로세스 | 웹 서버는 `V3_WORKER` 없이, 작업자는 `npx tsx scripts/v3-worker.ts` (같은 `MONGODB_URI`) | 웹과 다른 프로세스(다른 서버도 가능) | 웹과 계산을 나누고 싶을 때. 웹이 재시작해도 계산이 안 끊김 |
| C. 구간 호출 | `V3_WORKER_SECRET` 설정 후 외부 예약 호출이 `POST /api/v3/worker/tick` (머리글에 비밀값) | 호출 한 번 = 구간 하나 | 서버리스(Vercel). 함수 한 번이 5분 넘게 돌 수 있어야 함 |

- 어느 방식이든 작업 기록은 MongoDB에 있어서 섞어 써도 된다. 같은 작업을 둘이 가져가지 않는다(임대).
- 작업자가 갑자기 꺼져도 임대(기본 60초, `V3_LEASE_MS`)가 끝나면 다른 작업자가 중단점에서 이어 받는다.

### 9.2 서버에 필요한 것

| 항목 | 값 | 근거 |
|---|---|---|
| CPU | 계산 하나에 코어 1개 + 웹용 1개 | HiGHS JS는 단일 스레드 |
| 메모리 | 계산 하나에 최대 약 1 GB | 계산기 메모리 상한 1 GB에서 구간을 끝냄 (M6에서 프로세스 전체가 아니라 계산기 메모리 기준으로 바꿈) |
| 실행 시간 | 구간 하나 5분 + 저장 몇 초 | 방식 C는 함수 실행 시간 한도가 이보다 길어야 함 (요금제별 확인) |
| DB | MongoDB 그대로, 새 컬렉션 3개 (마이그레이션 없음) | `v3Jobs`·`v3JobResults`·`v3Checkpoints`(30일 TTL) |
| 사양 | 최소 2 vCPU·4 GB, 권장 4 vCPU·8 GB | 3절과 같음 |

참고 측정 (이 PC)
- 개발 서버(`next dev`)는 계산 없이도 약 700 MB를 쓴다. 배포 빌드(`next start`)의 웹 서버 메모리는 배포 단계에서 다시 잰다.
- 체험용 학교 정수계획 90초: 계산기 메모리 228 MB.

### 9.3 배포 전에 할 일

1. **계산 스레드 빌드**: 지금은 TypeScript 원본을 `tsx`로 실행한다(개발용). 배포에서는 `lib/v3/runner/engine-thread.ts`를 미리 JS로 빌드해 그 경로를 조정자에 넘기거나(`enginePath`), 작업자 실행에 `tsx`를 포함한다.
2. 방식 고르기: VPS면 A 또는 B, Vercel 유지면 C(실행 시간 한도·요금 확인).
3. 동시 계산 수를 코어 수에 맞추기 (`V3_WORKER_CONCURRENCY` = 코어 수 − 1).
4. 배포 빌드에서 웹 서버 메모리와 계산 중 응답 시간을 다시 재기 (`scripts/v3-perf/api-check.ts`).

> 후속: 사용자 조건(버셀 유지, 동시 10개 목표)에 맞춘 방안과 확정 사항은 [배포 방안](v3-deployment-plan.md)에 있다.
