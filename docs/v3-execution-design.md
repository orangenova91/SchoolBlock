# v3 5단계: 실행 구조 (2026-10-16)

## 0. 확정 사항 (사용자 결정)

- 여러 사용자가 동시에 쓴다. 서버 자원을 고려해 **작업 대기열(큐)을 쓴다**.
- 생성은 **작업 번호와 상태로 관리**하고, 화면은 주기적으로 진행 상태를 확인한다.
- 사용자는 화면에서 다음을 할 수 있다.
  - 중지 요청
  - 이어 돌리기 승인
  - 사전 승인(토글): 다음 구간을 미리 허락해 둠
- 계산 엔진은 JavaScript로 한다. 배포 서버에서 Python이 동작하는지 확인되지 않았기 때문이다.
- 배포 단계에서는 서버 환경과 제약을 확인한 뒤 다음 중 하나를 정한다.
  - 배포 방식 변경
  - 현 구조 최적화

## 1. 실험 결과

### 1.1 JS 엔진 (HiGHS WebAssembly) 대 Python (scipy HiGHS)

같은 수학 모델을 두 엔진에 넣어 비교했다. 둘 다 단일 스레드다.

| 비교 | JS | Python | 판단 |
|---|---|---|---|
| 배치 가능 판정 F1 / F7 / F9 | 38초 / 17초 / 512초 | 60초 / 24초 / 217초 | 비슷함 (0.6~2.4배) |
| 정수계획 단독 300초 K1 (최선 24) | 27 | 145 | 운에 따라 갈림. 둘 다 단독으로는 약함 (3단계와 같음) |
| 정수계획 단독 300초 K3 (최선 52) | 148 | 53 | 〃 |
| **혼합 225초, 같은 시작 해** K2 | 29 · 31 · 31 | 31 · 36 · 31 | JS 같거나 좋음 |
| **혼합 225초, 같은 시작 해** K4 (48반) | 44 · 27 · 64 | 57 · 51 · 103 | **JS가 좋음** (평균 45 대 70) |

JS 쪽 혼합이 좋은 이유는 두 가지다.
- 현재 해를 계산기에 시작점으로 넘길 수 있다(`setSolution`).
- 모델을 다시 만들지 않고 범위만 바꿀 수 있다(`changeColsBounds`).

그래서 같은 시간에 부분 재계산을 1.5~2배 더 했다.

또 JS 계산기는 계산 도중에 다음 두 가지를 지원한다. 중지 요청과 중단점 저장에 바로 쓸 수 있다.
- 계산 중단 (`mipInterrupt`)
- 개선된 해를 바로 받기 (`mipImprovingSolution`)

**결론: JS 엔진으로 충분하다. Python 없이 구현한다.**

### 1.2 중단점에서 이어 돌리기

연속 300초 실행과 "150초 → 중단점 저장 → 프로세스 종료 → 새 프로세스에서 150초"를 비교했다. 3회씩 반복했다.

| 방식·조건 | 연속 300초 | 150 + 150초 (중단점) | 이어 시작 점수 |
|---|---|---|---|
| 탐색 K2 | 39 · 29 · 51 (평균 39.7) | 45 · 37 · 39 (평균 40.3) | 멈춘 점수 그대로 |
| 탐색 K4 | 98 · 64 · 97 (86.3) | 92 · 72 · 92 (85.3) | 그대로 |
| 혼합(JS) K2 | 29 · 31 · 31 (30.3) | 29 · 31 · 31 (30.3) | 그대로 |
| 혼합(JS) K4 | 44 · 27 · 59 (43.3) | 50 · 27 · 58 (45.0) | 그대로 |

- 이어 돌린 프로세스는 12회 모두 **멈춘 점수에서 그대로** 시작했다. 중단점에서 잃는 것이 없다.
- 최종 품질 차이는 회차별 운의 범위 안이다.
- 모든 결과는 검증기를 통과했다.

**결론: 프로세스를 붙잡아 두지 않고, 중단점을 저장한 뒤 끝내고, 나중에 이어 돌려도 된다.**
정수계획법 단독은 탐색 나무(계산 진행 상태)를 저장할 수 없다. 그래서 이어 돌릴 때 현재 최선 해를 시작점으로 넣고 다시 계산한다. 하한도 다시 계산한다.

## 2. 작업(Job) 모델

### 2.1 저장 항목 (MongoDB `v3Jobs`, 마이그레이션 없음)

| 항목 | 내용 |
|---|---|
| 작업 번호 | `_id` (화면 표시는 학기 안 일련번호) |
| 학기·사용자 | `termId`, 요청한 사용자 |
| 방식 | `search` / `milp` / `hybrid` (버튼별) |
| 입력 지문 | 생성에 쓴 입력의 해시 (v2 캐시와 같은 방식). 입력이 바뀌면 이어 돌리기 불가 |
| 상태 | 2.2 참고 |
| 시간 | 누적 계산 시간, 현재 구간 번호, 구간 길이(5분), 최대 시간(30분 + 추가 승인분) |
| 사전 승인 | `autoContinue` 토글 (켜져 있으면 다음 구간을 자동으로 계속) |
| 진행 정보 | 단계(완성본 찾는 중·개선 중·판정 중·결과 모으는 중), 현재 최선 점수, 미배치 수, 이론상 최선(범위), 근접 여부, 모은 결과 수, 갱신 시각 |
| 결과 | 상위 3개 (점수·항목별 수치·방식·찾은 시각·시간표 칸) |
| 중단점 | 방식별 이어 하기에 필요한 것 (2.4) |
| 요청 표시 | 중지 요청, 이어 돌리기 승인 |
| 작업자 임대 | 맡은 작업자, 임대 만료 시각 (작업자가 죽으면 다른 작업자가 중단점에서 이어 받음) |

### 2.2 상태와 흐름

```
대기(queued) ──작업자가 가져감──▶ 실행(running) ──5분 구간 끝──┐
     ▲                                  │                        │
     │                                  │ 중지 요청               ├─ 사전 승인 켜짐 & 최대 시간 전 → 대기열로 (다음 구간)
     │                                  ▼                        │
     │                             중지됨(stopped)               ├─ 사전 승인 꺼짐 → 승인 대기(awaiting)
     │                                  │                        │
     └──── 이어 돌리기 승인 ────────────┴──── 승인 대기 ◀────────┘
                                                                 └─ 조기 종료 기준 충족 / 최대 시간 도달 → 완료(done)
완료·중지 상태에서도 사용자가 "이어 돌리기"를 승인하면 다시 대기열로 (입력이 바뀌지 않았을 때)
배치 불가 증명 → 실패(infeasible, 원인 안내) / 오류 → 오류(error)
```

- **구간이 끝날 때마다 중단점을 저장한다.** 승인을 기다리는 동안 프로세스를 붙잡아 두지 않는다. 작업자는 바로 다른 작업을 맡는다.
- 승인 대기 중인 작업은 사용자가 언제 승인하든 중단점에서 이어 간다.
  - 다시 시작하는 데 드는 시간: 모델 준비 1~5초 (실험: 탐색 초기화 0.4~1초, JS 모델 적재 0.03초)
- 진행 중에도 2~3초마다 진행 정보를 저장하고, 화면은 2~3초마다 상태를 확인한다.
- 중지 요청은 작업자가 1초 안에 알아챈다(탐색은 반복 중에 확인, 계산기는 `mipInterrupt`로 중단). 그 시점의 상위 3개와 중단점을 저장한다.

### 2.3 대기열과 작업자

| 항목 | 설계 |
|---|---|
| 대기열 | MongoDB 컬렉션 하나로 구현 (별도 서비스 없음). 작업자가 "가장 오래 기다린 대기 작업"을 원자적으로 가져간다 |
| 작업자 수 | 서버 CPU 코어 수에 맞춰 설정 (계산은 코어 하나씩 씀) |
| 공정성 | 작업은 5분 구간 단위로 실행하고, 다른 작업이 기다리면 구간이 끝난 작업은 대기열 뒤로 간다 (차례 돌리기). 큰 학교의 30분 작업이 다른 학교를 30분 막지 않는다 |
| 사용자당 제한 | 한 학기(학교)에 실행 중인 작업 1개, 대기 작업은 몇 개까지 (예: 3) |
| 장애 복구 | 작업자는 실행 중 임대 시간을 갱신한다. 끊기면 다른 작업자가 마지막 중단점에서 이어 받는다 |
| 실행 위치 | 작업자 코드를 독립 모듈로 만들어 두 방식 모두 가능하게 한다: Next.js 서버 안의 작업 스레드 / 별도 Node 프로세스. 선택은 배포 단계에서 |

### 2.4 방식별 중단점

| 방식 | 저장하는 것 | 이어 갈 때 |
|---|---|---|
| 탐색 | 현재 최선 시간표(공통 수업 칸 + SET 회차별 과목 담당), 상위 3개 | 최선 시간표에서 다시 데운 뒤(온도 재설정) 탐색 |
| 혼합 | 현재 해(변수 0/1), 상위 3개 | 그 해를 계산기 시작점으로 넣고 부분 재계산 반복 |
| 정수계획 | 현재 최선 해, 하한, 상위 3개 | 최선 해를 시작점으로 넣고 처음부터 계산 (탐색 나무는 저장 불가) |

중단점 크기는 시간표 하나에 수십~수백 KB다(48반 기준 변수 1만여 개의 0/1).

## 3. 화면 동작 (7단계 화면 설계의 입력)

| 요소 | 동작 |
|---|---|
| 방식 버튼 3개 | 탐색 / 정수계획 / 혼합. 누르면 작업 번호를 받고 대기열에 들어감 |
| 진행 패널 | 상태, 대기 순번, 경과/최대 시간, 단계, 현재 최선 점수, 이론상 최선(범위), 근접 여부, 결과 수 |
| 중지 | 중지 요청 → 그 시점 결과 표시 |
| 사전 승인 토글 | 켜 두면 5분 구간이 끝날 때 승인 없이 계속 (최대 30분까지. 30분 넘게는 따로 승인) |
| 승인 요청 | 구간이 끝났는데 토글이 꺼져 있으면 "5분 더 돌릴까요?" 표시. 언제든 승인 가능 (작업은 중단점으로 기다림) |
| 이어 돌리기 | 완료·중지·승인 대기 작업에서 5분 단위로 추가 (입력이 바뀌면 비활성: "입력이 바뀌어 새로 실행해야 합니다") |
| 결과 | 상위 3개 카드 (점수, 항목별 수치, 기준, 달성 여부) → 선택해 시간표로 보기·확정 |

## 4. 배포 단계에서 확인할 것

- 서버 종류(상시 실행 서버인지, 서버리스인지)와 CPU 코어 수, 메모리, 실행 시간 제한
- 별도 작업 프로세스를 띄울 수 있는지
  - 안 되면 Next.js 서버 안의 작업 스레드로 실행한다.
  - 서버리스라 긴 실행이 불가능하면 5분 구간을 더 짧게 쪼개는 방식으로 최적화한다. 중단점이 있어 가능하다.
- WebAssembly 메모리 제한 (48반 모델 기준 수십 MB 예상)

## 5. 결정 사항 (2026-10-16 확정: 기본값 적용, 보관 기간만 30일)

1. 승인 대기 중 프로세스 유지: **유지하지 않음 (즉시 중단점 저장 후 반납)**
2. 대기열 공정성: **5분 구간마다 차례 돌리기**
3. 사용자당 제한: **학기당 실행 1개 + 대기 3개**
4. 중단점 보관: **입력이 바뀌면 무효, 그 외 30일** (2026-10-16 확정)
