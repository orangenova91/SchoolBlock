## 0. 원칙

- **아래에서 위로 쌓는다.** 계산의 기초(검증기, 모델) → 계산 엔진 → 작업 관리 → API → 화면 순서로 만든다. 아래층이 검증된 뒤에 위층을 올린다.
- **v1·v2는 건드리지 않는다.** 예외는 정해 둔 세 곳뿐이다.
  - 홈 버튼과 v3 학기 이동
  - v1 레이아웃의 v3 자동 이동 한 줄
  - 학기 삭제 목록(`TERM_CHILD_COLLECTIONS`)에 새 컬렉션 추가
- **매 단계 끝에 확인한다.**
  - 새 자동 테스트
  - 기존 테스트 전체(`npm test`)
  - 실험 수치와 대조
- **실험 코드는 작업 폴더에 있다.** `sa.ts`, `model.py`, `highs-run.ts`, `quickcheck.ts`, `validate.ts`, `lns.py` 등을 옮겨 올 때 앱 코드 규칙에 맞게 다시 쓴다.
- Next.js 16은 바뀐 점이 많다. 라우트·레이아웃을 쓰기 전에 `node_modules/next/dist/docs/`의 해당 안내를 먼저 읽는다 (`AGENTS.md`).

## 1. 단계별 작업

### M1. 계산의 기초 (`lib/v3/`)

| 파일 | 내용 | 원본 |
|---|---|---|
| `input.ts` | 학기 입력 읽기(공용 해석 함수 사용), v3 해석(칠한 SET = 고정, 지정 순환 = 유지), 입력 지문(SHA-256) | v2 `timetable-check-cache.ts` 방식 |
| `validate.ts` | 명세 H1~H12, S1~S3 그대로 계산하는 검증기. 과목별 담당 교사로 겹침 검사, 순환 시수 검사 | 실험 `validate.ts` |
| `score.ts` | 점수와 항목별 수치(+α 교사 포함 명세 기준), 근접 판정(10%·6점 중 너그러운 쪽), 엄격 기준(5%·3점) | |
| `results.ts` | 상위 3개 관리: 30칸 그리고 5% 이상 차이, 비슷하면 같거나 좋을 때만 교체 | 정책 8.5 |
| `quick-check.ts` | 빠른 검사 5종 + 확정 부족 계산 | 실험 `quickcheck.ts` |
| `model.ts` | 정수계획 모델을 HiGHS(JS)에 넘길 형태(CSR)로 만듦. H12, 미배치 허용(보수용), 완화 모드(원인 찾기용) | 실험 `model.py` |

완료 기준:
- 검증기가 테스트 시간표 3·4의 저장 결과와 앱 진단 수치(점심 연강·3연강·동일 교과)에서 같은 값을 낸다.
- 빠른 검사가 F5에서 "최소 2", F9에서 "최소 4"를 낸다.
- 모델 점수와 검증기 점수가 같은 시간표에서 일치한다 (실험의 34 = 34 대조와 같음).

### M2. 계산 엔진 (`lib/v3/engines/`)

세 엔진이 같은 약속을 지킨다.
- 입력: 모델, 시작 해 또는 중단점, 구간 시간, 중지 신호
- 출력: 진행 보고(약 2초마다), 상위 3개, 중단점

| 파일 | 내용 | 원본 |
|---|---|---|
| `search.ts` | 탐색. 칸 맞바꾸기, SET 회차 이동, 순환 교사 맞바꾸기, H12, 규칙을 지키는 SET 시작 배치, 중단점에서 다시 데우기 | 실험 `sa.ts`, `order-test.ts` |
| `milp.ts` | 정수계획 단독. HiGHS JS, 개선 해 콜백, 중지(`mipInterrupt`), 시작 해 넣기 | 실험 `highs-run.ts` |
| `hybrid.ts` | 혼합. 탐색 → 구역 비우고 다시 계산(시작 해 넣기, 범위만 바꾸기), 막히면 구역 키우기, 불완전 시작 해 보수 | 실험 `highs-run.ts`, `lns.py` |
| `stop-rules.ts` | 조기 종료: 최선 도달·엄격 기준 도달 후 결과 3개 모으기, 30초·20회 추가 탐색 | 정책 8.5 |
| 메모리 관리 | 5분 구간마다 계산기(HiGHS)를 새로 만들어 메모리를 비움. 정수계획 단독은 메모리 상한(약 1 GB)을 넘으면 구간을 끝내고 중단점 저장 | [배포 검토](v3-deployment-review.md) 2절 측정: 60반 정수계획 5분에 계산기 내부 1.14 GB |

완료 기준:
- 성능 측정 스크립트 `scripts/v3-perf/`로 3단계 조건(K1~K4)을 다시 돌려 실험 결과와 비슷한 수준이 나온다.
  - K1 탐색 5분 24~27
  - K4 혼합 5분 평균 60 이하
- 중단점에서 이어 돌린 결과가 연속 실행과 같은 수준이다 (5단계 실험 재현).
- 모든 결과가 검증기를 통과한다.

### M4. 작업·대기열 (`lib/v3/jobs.ts`, `lib/v3/worker.ts`)

| 내용 | 설명 |
|---|---|
| 작업 저장·상태 전이 | `v3Jobs`. 상태가 맞을 때만 바꾸는 조건부 갱신 |
| 작업자 | 가장 오래 기다린 작업 꺼내기 → 한 구간 실행 → 진행 저장(2~3초) → 중단점·결과 저장 → 다음 상태 |
| 임대 | 실행 중 갱신, 끊기면 회수해서 중단점에서 재개 |
| 공정성·제한 | 구간마다 차례 돌리기, 학기당 실행 1 + 대기 3 |
| 중단점 | `v3Checkpoints`, 30일 자동 삭제(TTL 색인), 입력 지문이 다르면 이어 가기 거부 |
| 실행 방식 3종 | 별도 프로세스 스크립트, 서버 안 작업 스레드(`worker_threads`), 구간 호출(`/api/v3/worker/tick`) |

완료 기준:
- 작업자 두 개가 같은 작업을 동시에 가져가지 않는다.
- 작업자를 강제로 끝내도 다른 작업자가 중단점에서 이어 간다.
- 중지 요청을 1초 안에 처리한다.
- 계산 중에도 웹 요청이 막히지 않는다. 개발 서버에서 생성 중 다른 페이지가 열리는지 확인한다.

### M5. API (`app/api/terms/[termId]/v3/…`)

- 빠른 검사, 작업 만들기·목록·상태·사전 승인·중지·이어 돌리기, 결과 조회·적용, 진단 요청을 만든다.
- 학기 만들기·복제·가져오기에서 `logicVersion: "v3"`를 받는다.
- `TERM_CHILD_COLLECTIONS`에 새 컬렉션을 추가한다.

완료 기준:
- 로그인과 학기 소유 확인이 된다.
- v3가 아닌 학기에는 400을 낸다.
- 제한을 넘으면 409를 낸다.
- 결과 적용 시 검증기를 다시 확인하고, 확정 버전 메모를 자동 기록한다.

### M6. 화면 (`app/v3/terms/[termId]/…`, `components/v3/`)

| 화면 | 내용 |
|---|---|
| 레이아웃·단계 표시줄 | v3 전용, 기존 스타일 |
| 입력 화면 | 기존 입력 컴포넌트를 그대로 불러 씀 |

| 추가 조건 | 중요도, 항상 지키는 규칙, 목표 기준 설명 |
| 시간표 생성 | 빠른 검사, 방식 버튼 3개(혼합 추천), 진행 패널(2~3초마다 확인), 중지, 사전 승인, 승인 요청, 이어 돌리기, 작업 목록 |

- 배치 불가 조건에서 원인 안내까지

## 5. 진행 기록

### M1 계산의 기초 (2026-10-17 완료, 커밋 0ef3580)

- 검증기 = 앱 진단: 테스트 시간표 3·4 확정 35개 중 33개 일치. 나머지 2개는 만들 때 쓴 동일 교과 금지 목록이 저장 입력과 달라서이며, 점심 연강·3연강은 일치
- 빠른 검사: F5 최소 2, F9 최소 4 (2 ms)
- 모델 목적값 = 검증기 점수 (체험용 데이터 62)
- 결정
  - 선 수업이 고정 SET·배정 불가와 겹치면 빼지 않고 오류로 막는다 (데이터를 고쳐야 생성)
  - 점수는 +α 과목 교사까지 센다

### M2 계산 엔진 (2026-10-17)

5분(300초) 측정, `scripts/v3-perf/bench.ts`. 점수는 낮을수록 좋다.

| 조건 | 엔진 | 결과 | 3단계 실험(같은 시간) |
|---|---|---|---|
| K1 (21반, 제약 없음, 최선 24) | 탐색 | 27 · 27 · 24 · 29 · 33 | 24 · 27 · 24 |
| K2 (21반, 배정 불가·선 수업 5%) | 혼합 | 39 · 35 · 31 (보수 구역 추가 후) | 39 · 38 · 31 |
| K3 (K2 + SET 절반 고정) | 정수계획 | 45 (하한 42 증명, 엄격 기준 도달 후 조기 종료 238초) | 52* |
| K3 | 혼합 | 46 | 58 · 63 · 58 |
| K4 (48반) | 혼합 | 41 · 44 · 28 (평균 37.7) | 60 · 32 · 70 (평균 54) |
| K4 | 혼합, 150초 × 2구간 (중단점 JSON 저장 후 이어 감) | 33 · 55 · 27 (평균 38.3) | — |
| K5 (배치 불가, 최소 2) | 혼합 | 미배치 2~3 | 미배치 3 |

\* 3단계의 K3는 고정 SET의 순환 담당을 원래 지정(2학년 D SET은 미지정 → 담당 전원 바쁨)으로 둔 값이다.
v3 정책은 미지정 순환 담당을 생성기가 정하므로 더 낮아질 수 있다.

- 모든 결과가 검증기를 통과했다. 서로 다른 결과 3개를 모은다.
- 중단점에서 이어 간 두 번째 구간은 첫 구간의 최선 점수에서 시작했다. 연속 실행과 품질 차이는 회차별 운의 범위 안이다.
- 고친 문제 3가지
  - 혼합이 미배치 1을 5분 동안 못 고치던 경우: 미배치 수업의 반·교사·학년 SET을 비우는 "보수 구역" 추가
  - 같은 점수의 비슷한 결과로 바꿔 끼운 것을 "변화"로 세어 조기 종료가 안 되던 문제
  - 혼합의 메모리 상한(1.2 GB) 검사 추가 (측정 최대 1,056 MB). M6에서 프로세스 전체(rss)가 아니라 계산기(WebAssembly) 메모리 1 GB 기준으로 바꿈 (아래 M6 참고)
- 탐색은 같은 조건에서도 회차마다 차이가 크다 (K1 24~33).
  - 화면에서 방식 3개를 고를 수 있으므로 그대로 둔다.

### 테스트 시간표 5 분석 후 개선 (2026-10-18)

분석 ([테스트 시간표 5] 6·7·8반, 배정 불가 15칸): 적용 결과 0점 = 이론상 최선 0점(18초 증명), 검증기 위반 0. 다만
- 혼합이 0점을 75초에 찾고도 하한을 몰라 5분을 다 씀 (하한 계산이 생성 구간 뒤에 대기)
- **버그**: 정수계획이 최선을 증명하고 0.3초 만에 끝나도 "시간 다 씀"으로 보고 → 미리 승인이 켜진 작업이 71초 동안 구간 61번 반복

고친 것
- 정수계획이 최선을 증명하면 `optimal`로 끝내고 작업 완료
- **0점 = 늘 맞는 하한**: 생성 작업은 하한을 모르면 0을 하한으로 써서 조기 종료. 판정은 0점이면 최선, 6점 이하면 달성, 그 이상은 모름 (진단은 0 기준을 쓰지 않음)
- **하한 계산 동시 실행**: 같은 학기 1개 규칙에서 하한 계산은 따로 세어, 작업자에 빈자리가 있으면 생성과 동시에 돈다. 조정자가 2초마다 새 하한을 공유 메모리로 계산 스레드에 넘겨, 계산 중인 구간도 바로 쓴다

### 조기 종료 정책 개정·진단 정확도 (2026-10-18)

- 정책: [요구사항 8.5](v3-requirements.md) 개정. 엄격 기준 3개 → (추가 탐색 시) 최적해 3개. "30초 조용하면 끝" 규칙 삭제
- 코드: `StopRules`(목표 strict/optimal, exact), 작업 `goal` 저장, 추가 탐색 승인 시 목표 상향(`goalAfterApproval`), 더 계산할 것 없는 작업은 이어 계산 불가(`jobFinishedForGood`), 화면 안내·버튼 문구
- 진단은 일찍 끝내지 않음 (이론상 최선·고정의 영향)
- 빠른 검사 문구 수정: 교사의 학년 수업 = SET 밖 칸일 때 "배정 불가를 더하면 배치 불가"는 틀린 말이었다. 정확히는 "그 교사의 배정 불가 칸에는 반드시 (그 교사가 맡지 않는) 학년 전체 SET이 와야 함". 테스트 시간표 6(성하늘 교사 매일 1교시 배정 불가)은 실제로 배치 가능: 1교시에 C·D·E SET이 와서 24점 결과 3개
- 확인: 배정 불가 5칸을 더한 뒤 이론상 최선이 15점으로 "낮아진" 것은 계산이 덜 된 하한이다. 조건을 더하면 최선은 같거나 커지므로 최선 ≥ 24, 탐색이 24점을 찾아 최선 = 24. 일찍 끝내기를 끈 정수계획 5분도 하한 15에 머묾(배정 불가로 증명이 어려워짐). 반면 점심 연강만 최소화하면 37초에 "최소 8건"(× 중요도 3 = 24) 증명
