# 시간표 생성 로직 v3

v3는 같은 입력 단계(1~7단계)를 쓰면서 **SET 위치까지 생성이 정하는** 시간표 생성 로직이다.
v1·v2는 그대로 두고, 시간표마다 고른다(`terms.logicVersion = "v3"`).

- v1·v2 엔진은 수정하지 않았다. 공용 파일의 변경은 v3 시간표일 때만 동작이 달라진다 (11절).
- 저장 형식(현재 시간표·확정 버전)은 v1·v2와 같아서 기존 보기·내보내기를 그대로 쓴다.
- 목표: **모든 수업을 빠짐없이 놓은 시간표만** 만든다. 그 가운데 점수(피하고 싶은 일의 건수 × 중요도)가 가장 낮은 것을 찾는다.

자세한 설계 근거는 [요구사항](v3-requirements.md), [모델 명세](v3-model-spec.md), [알고리즘 비교](v3-algorithm-comparison.md), [진단 설계](v3-diagnosis-design.md), [실행 설계](v3-execution-design.md), [화면 설계](v3-screen-design.md), [진행 기록](v3-implementation-plan.md)에 있다.

## 1. 사용 방법

1. 목록 화면의 **새 시간표 작성(v3)** 으로 만든다. 목록과 단계 화면에 `v3` 표시가 붙고, 주소는 `/v3/terms/…` 이다.
   v3 시간표를 v1 주소로 열어도 같은 단계의 v3 화면으로 옮겨 간다.
2. 1~7단계는 v1과 같다. 다만 4단계 이름이 **SET 고정 배치**다.
   - 학교 사정으로 시간이 정해진 SET 칸만 칠한다. 칠한 회차는 고정된다.
   - 비워 둔 회차는 생성할 때 자동으로 놓는다. 자동 배치 버튼은 없고, 비워 둔 채로 다음 단계로 갈 수 있다.
3. 8단계 **시간표 생성**에서:
   1. 빠른 검사 결과를 본다. 오류가 있으면 생성 버튼이 잠긴다.
   2. 필요하면 조건별 중요도(1·2·3·5·10점)를 고른다.
   3. 계산 방법(혼합 추천·탐색·정수계획)을 누른다. 5분 단위로 계산하며 진행 상황을 보여 준다. 언제든 멈출 수 있다.
   4. 결과 3개를 비교해 **이 결과 적용**을 누른다. 그 결과가 현재 시간표가 되고, 확정 버전으로도 저장되며, 메모가 자동으로 적힌다.

## 2. 전체 흐름

```
[입력 1~7단계] ─ 저장할 때마다 입력 지문(해시)이 바뀜
[생성 화면 진입]
  └ 빠른 검사 (수 ms, 세어 보는 검사)
       ├ 확정 불가(입력 모순·시간 부족) → 생성 잠금 + 원인 목록 + 진단 안내
       └ 통과 → 방식 버튼 사용 가능
[방식 버튼]
  └ 작업을 대기열에 넣음 (학기당 실행 1 + 대기 3)
  └ 같은 입력의 이론상 최선이 없으면 "하한 계산(2분)" 작업도 함께 넣음
[작업자] (웹 서버와 분리된 계산 스레드)
  └ 5분 구간 계산 → 결과 3개·중단점 저장
       ├ 목표 달성 + 서로 다른 결과 3개 → 완료 (조기 종료)
       ├ 미리 승인 켬 → 최대 30분까지 이어 계산
       └ 미리 승인 끔 → 승인 대기 ("5분 더 계산"을 누르면 중단점에서 이어 감)
[결과 적용]
  └ 검증기로 다시 확인 → 현재 시간표 + 확정 버전 (메모 자동)
```

## 3. 규칙 (무엇을 반드시 지키고, 무엇을 점수로 줄이나)

### 3.1 반드시 지키는 것 (어기면 "미배치")

| 규칙 | 뜻 |
|---|---|
| 시수 | 교과마다 정한 주당 시간을 모두 놓는다 |
| 반·교사 겹침 | 한 반, 한 교사는 한 칸에 수업 하나 (SET 담당 교사 포함, 모든 학년 합산) |
| 배정 불가 | 교사가 안 되는 칸에는 그 교사 수업을 놓지 않는다 |
| 선 수업 | 미리 놓은 칸은 그대로 |
| SET | 회차 수를 지키고, 고정한 회차는 그 자리. 학년 전체 SET과 부분 SET은 같은 칸 불가 |
| 순환 교사 | SET 과목을 여러 교사가 돌아가며 맡으면, 회차마다 1명. 교사별 시수 유지. 사용자가 지정한 칸은 그대로 |
| 같은 SET 요일 배분 | 같은 SET은 하루 한 번이 원칙이다. 회차가 요일보다 많으면 층을 쌓듯 고르게 더한다. 고정한 요일에는 자동으로 더하지 않는다 |

**미배치가 하나라도 있으면 시간표를 만들지 않는다.** 미배치 1시간은 1,000점으로 계산해, 어떤 선호 점수보다 나쁘게 한다.

### 3.2 점수로 줄이는 것 (낮을수록 좋음)

| 항목 | 1건 | 기본 중요도 |
|---|---|---|
| 점심시간 연강 | 교사가 점심 앞뒤 교시를 모두 수업 | 3 |
| 3연강 | 교사가 점심을 걸치지 않고 3교시 연속 수업 (4연속 = 2건) | 2 |
| 동일 교과 같은 날 | 고른 교과가 한 반 한 요일에 2시간 이상 | 3 |

- 점수 = Σ 건수 × 중요도. **+α 과목 교사를 포함한 모든 교사**를 센다.
- 추가 조건에서 끈 항목은 중요도 0이다.
- 건수는 앱 공통 진단 함수(`listLunchTeacherDoubles` 등)와 같은 값이다.

### 3.3 목표 기준

- **이론상 최선(하한)**: "어떤 방법으로도 이보다 좋을 수 없다"는 점수다. 정수계획 계산이 증명한다.
- **근접 기준(목표)**: 점수 ≤ max(하한 × 1.1, 하한 + 6) 이면 목표 달성이다.
- **엄격 기준**: max(하한 × 1.05, 하한 + 3). 조기 종료에 쓴다.
- 결과는 늘 점수와 기준을 함께 보여 준다. 예: "30점 · 목표 29점 이하 · 목표까지 1점".

비유: 하한은 "이 코스는 아무리 빨라도 23분"이라는 증명이고, 근접 기준은 "29분 안에 들어오면 잘 뛴 것"이라는 합격선이다.

## 4. 빠른 검사 (`lib/v3/quick-check.ts`)

시간을 세어 보기만 하는 검사로, 몇 ms에 끝난다. 화면에 들어올 때와 생성 버튼을 누를 때 실행한다.

| 규칙 | 뜻 | 정도 |
|---|---|---|
| 반 시간 | 반 수업 시간 > 칸 수 | 오류 |
| 교사 시간 | 교사 수업 > 배정 가능한 칸 | 오류 |
| 교사의 학년 수업 | 교사의 한 학년 수업 > 그 학년 전체 SET 밖 칸 (같으면 경고) | 오류/경고 |
| 학년 전체 SET 칸 | 학년 전체 SET 회차를 놓을 빈 세로줄 부족 | 오류 |
| SET 칸·요일 | SET을 놓을 칸 또는 요일(하루 1회) 부족 | 오류 |
| 고정 SET 충돌 | 고정한 SET 칸이 선 수업·담당 교사 배정 불가와 겹침 | 오류(입력 모순) |
| 선 수업 충돌 | 선 수업이 고정 SET·배정 불가·다른 선 수업과 겹침 | 오류(입력 모순) |

통과해도 실제 배치가 안 될 수 있다. 세는 검사는 "칸끼리 서로 맞물리는 문제"를 보지 못한다(예: F7).
그때는 생성 결과가 "완성본을 못 찾음"으로 끝나고, 화면이 원인 찾기를 안내한다.

## 5. 계산 방법 (`lib/v3/engines/`)

| 방법 | 어떻게 | 강점 | 약점 |
|---|---|---|---|
| **혼합 (추천)** `hybrid.ts` | 탐색으로 시작 해를 만든 뒤, 한 구역(하루, 한 학년의 이틀, 오래 못 좋아지면 더 큰 구역)만 비우고 정수계획으로 그 구역을 다시 최적으로 채우기를 반복 | 큰 학교에서도 꾸준히 좋아짐 (48반 5분 평균 38점, 실험 원형 54점) | 하한은 스스로 증명하지 못함 (하한 계산 작업이 따로 함) |
| 탐색 `search.ts` | 담금질 탐색. 반 안 두 칸 맞바꾸기, 학년 세로줄(SET 회차) 맞바꾸기, 순환 교사 맞바꾸기 | 완성본을 빨리 찾음 | 좋은 답 근처에서 오래 맴돎 |
| 정수계획 `milp.ts` | 시간표 전체를 수식 하나로 풀기 (HiGHS, 탐색 해로 시작) | 작은 학교에서 최선 증명까지 가능, 하한 계산 | 큰 학교는 느리고 메모리를 씀 |

비유: 혼합은 방 전체를 한 번에 정리하지 않고 서랍 하나씩 꺼내 완벽하게 정리해 다시 넣는 방식이다. 서랍(구역)이 작아서 정밀 계산이 빨리 끝난다.

- 미배치가 남으면 혼합은 **보수 구역**을 자주 쓴다. 남은 수업의 반 전체, 그 교사의 모든 수업, 그 학년 SET을 한꺼번에 비운다.
- 계산기 메모리(WebAssembly)가 1 GB를 넘으면 구간을 끝내고 중단점을 저장한다. 프로세스 전체가 아니라 계산기 자신의 메모리만 본다.

### 5.1 결과 3개 (`lib/v3/results.ts`)

- 점수 순 상위 3개를 모은다. 서로 **30칸 이상이면서 5% 이상** 달라야 한다. 같은 시간표를 조금만 바꾼 것은 하나로 본다.
- 점수가 같거나 더 좋은 비슷한 결과는 기존 것을 바꿔 넣는다.

### 5.2 조기 종료 (`stop-rules.ts`)

1. 하한을 알고, 최고 점수가 엄격 기준(최선에 닿았으면 하한) 안에 들면 "모으기" 단계로 들어간다.
2. 기준 안의 서로 다른 결과 3개가 모이면 끝낸다.
3. 3개가 안 모여도 상위 목록이 30초 동안 바뀌지 않고 (혼합·정수계획은) 부분 계산을 20회 이상 했으면 끝낸다.
4. 하한을 모르면 조기 종료하지 않는다.

## 6. 작업과 대기열 (`lib/v3/jobs.ts`, `lib/v3/runner/`)

| 항목 | 값 |
|---|---|
| 구간 | 5분. 끝날 때마다 결과 3개·중단점 저장 |
| 최대 | 30분 (다 쓴 뒤에도 승인하면 5분씩 더) |
| 미리 승인 | 켜면 30분까지 묻지 않고 이어 계산 |
| 중단점 | 30일 보관, 입력이 바뀌면 이어 계산 불가 |
| 대기열 | 학기당 실행 1 + 대기 3. 여러 학기는 구간 단위로 번갈아 실행 |
| 하한 계산 | 생성 작업을 만들 때 같은 입력의 하한이 없으면 2분짜리를 자동으로 넣음. 계산 도중 오르는 하한도 바로 씀 (도중 값도 증명된 값). 진단 버튼으로 직접 돌리면 10분 |
| 중지 | 1초 안에 계산 스레드에 전달, 그때까지의 최선을 저장 |

실행 구조: 조정자(coordinator)가 대기열에서 작업을 꺼내 **계산 스레드**(worker_threads)에 맡긴다.
조정자는 DB 읽기·쓰기만 하므로 웹 요청을 막지 않는다. 측정: 계산 중 웹 응답 중앙값 27 ms.
같은 코드를 세 가지 방식으로 돌릴 수 있다 (12절).

## 7. 진단 (`lib/v3/diagnose.ts`, 요청 시 실행)

| 진단 | 답하는 질문 | 방법 |
|---|---|---|
| 배치 가능 판정 | 모든 수업을 놓을 수 있나? | 빠른 검사 → 탐색(첫 완성본이 나오면 증명) → 정수계획 정확 판정. 안 되면 끝까지 남는 수업 |
| 풀어야 할 조건 찾기 | 무엇을 풀면 되나? | 배정 불가·선 수업을 "풀 수 있음"으로 두고 푸는 개수를 최소화. 시간 수 자체가 모자라면 계산 없이 "풀어도 안 됨" |
| 고정의 영향 | 고정한 SET 때문에 몇 점 손해인가? | 고정 그대로의 최선과 고정을 푼 최선을 비교 (범위) |
| 데이터 한계 | 입력상 피할 수 없는 건수는? | 항목별 최소화 + 점심 연강 세기 설명 |
| 이론상 최선 | 목표 기준 | 정수계획 하한 |

결과는 입력 지문과 함께 저장되어, 입력이 바뀌기 전까지 다시 계산하지 않고 보여 준다.

## 9. API (`app/api/terms/[termId]/v3/…`)

| 창구 | 내용 |
|---|---|
| `GET checks` | 빠른 검사, 입력 지문, SET 고정 현황, 같은 입력의 최근 진단 |
| `GET·PUT settings` | 중요도 |
| `GET·POST jobs` | 작업 목록·만들기 (빠른 검사 확정 불가 409, 대기 초과 409, 하한 작업 자동 추가) |
| `GET·PATCH jobs/[jobId]` | 상태, 미리 승인 토글 |
| `POST jobs/[jobId]/stop`·`continue` | 중지, 이어 계산 (입력이 바뀌면 409) |
| `GET jobs/[jobId]/results`, `POST …/results/[rank]/apply` | 결과 3개, 적용 (검증기 재확인) |
| `POST /api/v3/worker/tick` | 구간 호출용 (`V3_WORKER_SECRET` 있을 때만) |

v1 생성 창구(`timetable` POST, 점심·같은 날 우선 배치)는 v3 시간표면 400을 돌려준다.

## 10. 측정 결과 요약

M7 확인 (2026-10-17, 이 PC, 개발 서버 안 작업자 1개, `scripts/v3-perf/e2e-check.ts`). 혼합 1구간(5분) → 자동 하한(2분) → 결과 1번 적용.

| 시간표 | 규모·조건 | 혼합 5분 결과 | 하한 (2분) | 판정 |
|---|---|---|---|---|
| 테스트 시간표 3 (v2 시간표를 v3로) | SET 8개 모두 고정 | 6·6·6점 (1번과 다른 칸 320·260) | 6 | **최선 증명** |

## 13. 한계와 남은 과제

- 계산 스레드는 TypeScript 원본을 `tsx`로 실행한다 (개발용). 배포할 때는 미리 빌드해야 한다.
- 혼합은 스스로 하한을 증명하지 못한다. 그래서 하한 계산 작업이 생성 구간 사이에 돈다. 같은 학기에서는 한 번에 하나만 돌기 때문에, 첫 구간은 목표를 모른 채 계산한다.
- 큰 학교(48반)의 하한은 2분 안에 약하게 나올 수 있다. 그러면 목표 기준이 느슨해진다 (진단으로 10분 계산 가능).
- 결과를 적용한 뒤 칸 바꾸기(미세 조정)는 v1 화면에만 있다.
