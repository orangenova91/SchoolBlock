# v4 검토 (2026-10-19, 정리만 — 결정 보류)

v3는 **목표 시간표를 정확하게 찾는 것**은 달성했다. 같은 학교에서 v2보다 점수가 크게 낮고, v2로는 배치할 수 없던 학교도 완성한다 ([v3 계산 시간 안내](v3-timing-guide.md) 3-4).
남은 문제는 **시간**이다. v2는 30초 안에 끝나는데, v3는 목표·최선까지 보통 1~5분, 큰 학교는 15분에도 못 닿는 경우가 있다.

작은 수정으로 되는 개선은 v3에 넣었다: 30반 이하 혼합의 시작 해 탐색 75초 → 20초, 목표 도달 중앙 52초 → 18초 (3-5·3-6).
아래는 **로직이나 배포 구조를 크게 바꿔야 하는 방안**이라 v4로 넘긴 것이다. 배포 구조 변경·Python 사용·모델 재구성은 지금 결정하지 않고 v4에서 상세 검토한다.

---

## 1. 한 작업에 계산 2개 동시 실행 (포트폴리오)

**내용**: 같은 학교를 혼합과 정수계획(또는 다른 무작위 시작값의 혼합 2개)으로 동시에 계산한다. 좋은 결과를 서로 나눠 쓰고, 둘 중 좋은 쪽을 결과로 쓴다.

**기대 효과**
- 중간 학교에서 혼합이 좋은 답 근처에서 멈추는 경우를 정수계획이 보완한다 (측정: 18곳 중 3곳은 정수계획이 1.5~5.5점 더 좋은 최선).
- 같은 학교라도 회차마다 결과 차이가 크다 (예: 60반 혼합 5점 / 20점). 2개를 돌려 좋은 쪽을 쓰면 나쁜 회차를 피한다.

**바뀌는 것**
- 작업 하나가 계산 스레드 2개를 쓴다 → 동시 계산 상한을 "작업 수"가 아니라 "코어 수"로 세야 한다.
- 버셀 Pro 함수는 2 vCPU까지 쓸 수 있어, 함수 하나 안에서 2개를 돌릴 수 있다.
- 결과 공유(한쪽이 찾은 좋은 해를 다른 쪽 시작점으로)는 조정자·계산 스레드 구조를 고쳐야 한다.

**판단 근거로 필요한 것**: 혼합 2개(다른 시작값) 대 혼합+정수계획 대 혼합 1개를 같은 CPU 예산으로 비교한다.

**참고**: "혼합 5분 → 정수계획이 이어 받기"(B안)는 이미 측정했다. 큰 학교에서 혼합만 계속 돌린 것보다 나쁜 곳이 많아(20곳 중 10곳) 쓰지 않기로 했다. 동시 실행은 순서가 아니라 **함께** 돌린다는 점이 다르다.

## 2. 다른 계산기: 제약 계산기 (예: OR-Tools CP-SAT)

**내용**: 지금은 정수계획 계산기(HiGHS, WebAssembly)를 쓴다. 시간표처럼 "칸에 무엇을 놓을까"라는 문제에는 제약 계산기가 강한 경우가 많다. 제약 계산기는 여러 코어로 동시에 탐색하고, 좋은 해를 빨리 찾는 기법이 많다.

**기대 효과**: 큰 학교에서 시간이 크게 줄 가능성. 실제 효과는 같은 학교로 시험해 봐야 안다.

**바뀌는 것**
- OR-Tools CP-SAT은 공식 JavaScript(WebAssembly) 판이 없다. **Python 또는 C++ 계산 서버**가 필요하다.
- 계산 서버를 버셀 함수(Python 지원)로 둘지, 별도 서버로 둘지 정해야 한다. 버셀 Python 함수의 실행 시간·메모리 한도 안에서 도는지 확인해야 한다.
- 계산 모델(제약 조건)을 새 계산기 형식으로 다시 써야 한다. 검증기·점수·결과 저장은 v3 것을 그대로 쓸 수 있다.

**판단 근거로 필요한 것**: 체험용 20반·가상 24·48반으로 CP-SAT 원형을 만들어 v3 혼합과 시간·점수를 비교한다.

## 3. 모델 재구성

지금 정수계획 모델은 "공통 수업을 어느 칸에 / SET 회차를 어느 칸에 / 순환 담당을 누구에게"를 칸 단위 변수로 둔다. 큰 학교에서 정수계획이 첫 결과에서 거의 움직이지 않는 원인 중 하나가 변수가 너무 많고 비슷한 해가 너무 많기 때문이다.

| 방안 | 내용 | 기대 효과 |
|---|---|---|
| SET 회차를 "시간 묶음" 단위로 | 학년 전체 SET은 학년 전체 칸을 함께 차지하므로, SET 위치를 먼저 "어느 요일 몇 교시 묶음"으로 정하는 상위 문제와 나머지 배치 문제로 나눈다 | 큰 학교에서 SET 위치 결정이 가벼워짐 |
| 같은 모양 반·교사의 중복 제거 | 같은 수업 구성의 반들은 서로 바꿔도 같은 시간표다. 이런 중복을 제약으로 줄인다 | 정수계획이 같은 해를 여러 번 보지 않음 |
| 단계별 풀이 | 점심 연강 → 3연강 → 같은 날 교과 순으로 하나씩 최소화하며 고정 (이론상 최선의 항목별 최소와 같은 생각) | 큰 학교에서 단계마다 문제가 작아짐 |
| 하한 강화 | 지금 하한은 "항목별 최소의 합"과 전체 계산 중 큰 값. 교사별·요일별 세기 하한을 더 넣는다 | 목표 기준이 정확해져 일찍 끝날 수 있음 |

**바뀌는 것**: 모델·엔진 대부분을 다시 설계하고, 검증기와 결과를 비교하는 회귀 측정을 다시 해야 한다.

## 4. 작게 남은 개선 (v3 안에서 할 수도 있음)

| 방안 | 측정 결과 | 상태 |
|---|---|---|
| 탐색을 1분마다 다시 데우기 | 처음 1분 결과가 크게 좋아짐(1분 시점 차이 139 → 9.8점), 5분 결과는 비슷 | 넣지 않음. 탐색 버튼을 화면에 남기면 넣을 만함 |
| 큰 학교 혼합의 준비 시간을 반 수에 비례 | 31반 이상은 75초 유지. 20초는 크게 나쁜 회차가 있었음 | 측정 더 필요 |
| 혼합 부분 재계산 한 번의 시간(15초)·구역 크기 조정 | 측정 안 함 | 후보 |

## 5. 결정할 것 (v4 착수 때)

1. 계산을 어디서 돌릴지: 버셀 함수만(JavaScript) / 버셀 함수 + Python 함수 / 별도 계산 서버
2. 계산기: HiGHS 유지(모델 재구성) / 제약 계산기 도입 / 둘 다 시험
3. 작업당 코어 수: 1개(지금) / 2개(포트폴리오)
4. 비교 기준: v3 측정 도구(`scripts/v3-perf/sweep.ts`, `compare-versions.ts`)와 같은 학교 조건으로 시간·점수 비교
